# How does each caller prove who it is?

Authentication answers "who is calling, and on whose behalf?". Authorisation (`06-authorisation-checks.md`) answers "may they do this?". Keep them apart in findings: a perfectly identified caller can still be over-privileged, and a well-designed permission model is worthless if identity can be faked.

## Two identities per call
Most API calls carry up to two identities, and reviews go wrong when they are blurred:
- the **client**: the application or workload making the request;
- the **subject**: the person (or organisation) the request acts for.

A partner's back-office system acting for itself has only a client identity. A third-party app acting for a pet owner has both. A rule Argus applies without exception: **the subject must come from something the subject or a trusted issuer produced (a token, a signed assertion), never from a field the client fills in.** A partner that can send `X-Customer-Id: 4711` alongside its own API key can act as every customer.

## The MIKA credential ladder
Credentials ranked by how much a thief gains and how long it lasts. Use it to say "move one rung up" in a fix.

| Rung | Credential | What a stolen copy gives | Fit |
|---|---|---|---|
| 0 | None | everything | D0 reads only |
| 1 | Password sent per request (HTTP Basic) | long-lived account access, reusable elsewhere | internal tooling at most; never for third parties |
| 2 | Static API key | the client's access until someone notices | metering and low-risk D0/D1 access |
| 3 | Shared client secret exchanged for short-lived tokens | new tokens until the secret is rotated | confidential clients at D1–D2 |
| 4 | Asymmetric client authentication (`private_key_jwt` per RFC 7523, or mutual TLS per RFC 8705) issuing short-lived bearer tokens | short-lived tokens; the key itself never travels | partners and workloads at D2–D3 |
| 5 | Sender-constrained tokens (DPoP per RFC 9449, or certificate-bound per RFC 8705) | nothing without the private key | D3–D4, third parties, FAPI profiles |

Rung 5 also covers workload identities issued automatically by a platform (SPIFFE SVIDs; see `09-transport-and-workload-identity.md`).

## If API keys are used, what must be true?
- Identify a **client or project**, never a person.
- Generated by a CSPRNG with at least 128 bits of entropy; carry a recognisable prefix so secret scanners (and platform push-protection) can spot leaks.
- Sent in a header only, never in a URL; stored hashed on the server.
- Scoped to the minimum operations; rate-limited per key.
- Rotatable without downtime (two keys valid during the overlap) and revocable at once.
- Listed in an inventory with an owner and an expiry.

## People: how strong must sign-in be?
- Delegate sign-in to a mature identity provider through OpenID Connect (`05-delegated-access-flows.md`). Home-built password handling inside an API is a finding.
- MFA for D3; phishing-resistant authenticators (passkeys / WebAuthn, FIDO2 keys) or a step-up for D4 actions.
- APIs can demand a stronger sign-in for a single operation with the OAuth step-up challenge (RFC 9470): the resource server answers `401` with `error="insufficient_user_authentication"` and the required `acr_values` or `max_age`, and the client sends the person back to sign in again.
- Login, token, one-time-code, password-reset and signup endpoints need their own tight rate limits and monitoring (CWE-307).
- Responses must not reveal whether an account exists (CWE-204).

## Machines: how does a workload or partner prove itself?
- Machine-to-machine calls use the client-credentials grant, authenticated at rung 4 or above.
- Inside a platform, prefer identities the platform issues and rotates (SPIFFE/SPIRE, cloud workload identity federation, managed identities) over secrets someone has to store.
- mutual TLS proves which workload is calling, not on whose behalf. When the subject matters downstream, pass a verified token as well (token exchange per RFC 8693 narrows it per hop).

## Inbound webhooks
Verify an HMAC or asymmetric signature over the raw body plus a timestamp, reject outside a replay window of a few minutes, deduplicate on an event ID, rotate signing secrets with overlap, and still treat the payload as untrusted input (`API10:2023`).

## Findings Argus raises here, with a typical starting rating
| Finding | Typical rating before scoring |
|---|---|
| Subject taken from a client-set header or body field | Critical on D3/D4, High on D2 |
| No authentication on a D2+ operation | Critical |
| Password sent per request to a third-party-facing API | High |
| API key used as a person's identity | High |
| Shared secret where asymmetric client auth is available, at D3+ | Medium |
| Sign-in endpoints without dedicated limits | High |
| Internal calls unauthenticated because "inside the cluster" | Medium; High at D3+ |
Confirm every rating with the scoring rule in `11-severity-and-verdict.md`.
