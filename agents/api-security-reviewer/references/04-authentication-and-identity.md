# Authentication and identity for APIs

**Authentication** establishes who is calling (a person, an application, or a workload). **Authorisation** decides what that caller may do (`07-authorization.md`). Keep them separate in reviews: a perfectly authenticated caller can still be over-privileged.

## Who is the caller?
| Caller type | Typical identity | Typical mechanism |
|---|---|---|
| End user via your own app | User + client app | OAuth 2.x authorization code + PKCE, OIDC for identity |
| End user via a third-party app | User + third-party client, with user consent | Authorization code + PKCE, scopes, consent screen |
| Partner/back-end system acting for itself | Client (application) | Client credentials grant, ideally with `private_key_jwt` or mTLS client authentication |
| Internal service-to-service | Workload identity | mTLS with workload certificates (e.g., SPIFFE IDs via a mesh), plus a token if user context must propagate |
| Device with limited input | Device + user | Device authorization grant |
| Webhook sender (you receive) | Sending platform | Signed payloads (HMAC or asymmetric) with timestamp and replay window, optionally mTLS |

## Mechanisms and their limits
- **Username/password per request (HTTP Basic)**: sends a long-lived credential on every call and forces users to hand passwords to any app that calls on their behalf. Not acceptable for APIs that third parties call; at most for tightly controlled internal tooling, and even there prefer tokens.
- **Opaque tokens with server-side lookup**: simple and revocable instantly, but every request needs a lookup (latency, availability dependency) unless cached. Token introspection (RFC 7662) is the standard way.
- **Self-contained tokens (JWT)**: verified in-process with a public key; no lookup; harder to revoke, so keep them short-lived (`06-tokens-and-jwt.md`).
- **API keys**: identify an application or project, not a user. Acceptable for low-risk, read-only or metering use. Requirements if used: generated by a CSPRNG with ≥128 bits of entropy (32+ random characters is common), sent only in a header (never in URLs), stored hashed server-side, scoped to the minimum, rotatable without downtime (support two active keys), revocable, prefixed so leaked keys can be detected by secret scanners, rate-limited per key.
- **The key-plus-user anti-pattern**: a third party holding an API key must not be able to assert *which user* it acts for (e.g., by sending a user ID header). That hands control of every user's account to the third party. Delegated user access needs a user-granted token (OAuth).
- **MFA**: raises assurance for user logins; high-value APIs can require it by checking an authentication-method claim (`amr`/`acr`) and stepping up when absent. Phishing-resistant methods (passkeys/WebAuthn) are the current direction (general knowledge).

## Mutual TLS and workload identity
- TLS authenticates the server; **mTLS** also authenticates the client by certificate. Strong for machine-to-machine and service-to-service traffic.
- Running mTLS by hand is operationally hard (certificate issuance, rotation, revocation across languages). A **service mesh** data plane (sidecar or node proxy) can issue workload identities (e.g., SPIFFE), rotate short-lived certificates automatically and enforce mTLS without code changes, plus service-level authorisation policies.
- mTLS proves *which workload* is calling, not *on whose behalf*. When user context matters downstream, propagate a token as well (and validate it, see token exchange in `05-oauth-and-oidc.md`).
- At the edge, **certificate-bound tokens** (RFC 8705) combine OAuth with mTLS so a stolen token is useless without the client's private key.
- Check: who issues certificates, lifetime, rotation, what happens when the CA or mesh control plane fails, whether plaintext is still allowed ("permissive mode") anywhere.

## Transport
- TLS everywhere tokens or personal data travel, including internal hops in zero-trust designs. TLS 1.2 minimum with modern cipher suites, TLS 1.3 preferred; disable older versions; HSTS for browser-facing hosts.
- Never put credentials or tokens in URLs or query strings (they end up in logs, proxies, browser history, Referer headers).

## Review questions
1. For each flow crossing a trust boundary: what credential authenticates the caller, and how is it validated?
2. Is user identity ever asserted by a client-controlled field instead of a verified token?
3. Are any long-lived shared secrets used where short-lived or asymmetric credentials are possible?
4. How are credentials rotated and revoked, and how fast?
5. Are login, token, OTP and password-reset endpoints rate-limited and monitored?
6. Is any internal traffic unauthenticated because "it's inside the cluster"?
