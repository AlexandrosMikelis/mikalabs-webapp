# Resources, naming and HTTP semantics

## Resource modelling
- Model **nouns from the consumer's domain**, not database tables, internal services or UI screens. Ask: what does the consumer need to find, create, change and observe?
- Collections are plural nouns (`/attendees`), items are addressed by an identifier (`/attendees/{attendeeId}`). Nest only to express real ownership, and keep nesting shallow (one level is usually enough: `/conferences/{id}/sessions`).
- Use **opaque, stable identifiers** generated by the producer. Don't use email, national ID or other personal data as an ID or in any URL (paths and query strings end up in logs, caches and browser history).
- Operations that don't fit CRUD: prefer modelling the outcome as a resource (`POST /payments/{id}/refunds`) over verbs in paths. If a custom action is unavoidable, use one consistent convention (e.g., Google AIP `POST /orders/{id}:cancel`).
- One concept, one name, one shape across the whole API. A field called `customerId` in one place and `clientRef` in another is a defect.

## Naming
- Pick one case convention for fields (camelCase is most common in JSON; snake_case is fine if consistent) and one for paths (kebab-case or lowercase).
- Maintain a **domain data dictionary** on top of the chosen guideline: standard names for recurring concepts (IDs, timestamps, money, addresses, status). Use established industry vocabulary where it exists.
- Names are part of the contract: renaming a field later is a breaking change, so get them right early.
- General knowledge conventions: timestamps in RFC 3339 / ISO 8601 UTC (`createdAt`); money as amount (decimal string or integer minor units) plus ISO 4217 currency, never floats; booleans named as predicates (`isActive` or `active`, consistently); enums as strings, documented as extensible; avoid abbreviations.

## Methods and their semantics (RFC 9110, general knowledge)
| Method | Use | Safe | Idempotent | Notes |
|---|---|---|---|---|
| GET | Read | yes | yes | Never changes state; cacheable; no body |
| POST | Create in a collection, or trigger a process | no | no | Make it idempotent with an `Idempotency-Key` where retries are likely (see 04) |
| PUT | Replace a resource entirely (or create at a client-chosen URI) | no | yes | Missing fields mean "removed", which surprises consumers; say so |
| PATCH | Partial update | no | not inherently | Specify the format: JSON Merge Patch (RFC 7396) or JSON Patch (RFC 6902) |
| DELETE | Remove | no | yes | Second call: 404 or 204, document which |
- A GET that changes state, or a POST used for every read, is a Level 0/1 design and breaks caching, retries and intermediaries.
- Prefer PATCH over PUT for partial updates; agree this in contract discussions.

## Status codes (common, general knowledge)
- **200** OK with body; **201** Created + `Location` header pointing at the new resource; **202** Accepted for asynchronous work (return a status resource); **204** No Content.
- **400** malformed or invalid request; **401** not authenticated; **403** authenticated but not allowed; **404** not found (also used to avoid revealing existence); **405** method not allowed; **409** conflict with current state; **412** precondition failed (ETag mismatch); **415** unsupported media type; **422** semantically invalid (if the standard uses it); **429** too many requests.
- **500** unexpected server error; **502/503/504** upstream or availability problems (503 with `Retry-After`).
- Consumers build logic on status codes. **Never return an error inside a 2xx response.** Redirects (3xx) are followed automatically by many clients; use them deliberately.
- Empty collections return 200 with an empty list, not 404. Document it either way.

## Headers and content
- `Content-Type` / `Accept` for content negotiation; return a media type the consumer can actually parse (JSON for machine consumers; a PDF is valid but not integration-friendly).
- `Location` on create; `ETag` / `If-Match` for concurrency; `Cache-Control` for cacheability; `Retry-After` on 429/503.
- Correlation: accept and propagate a request ID / W3C `traceparent` for tracing.

## Long-running operations
- Don't hold a request open for minutes. Return **202 Accepted** with a link to an operation/status resource the consumer can poll, or offer a callback/webhook or event. Document terminal states, timeouts and how results are retrieved (Google AIP-151 and Microsoft guidelines describe this pattern).

## Consistency rules for a review
- Same pagination, error, naming, date and money conventions everywhere.
- Every operation documents success and error responses.
- No internal artefacts in the contract (table names, ORM fields, stack-specific types, internal hostnames).
