# Flow requirements

Six requirement areas decide whether a flow is trusted and operable. Use them as the checklist in `design` (one line each) and as review areas in `review`.

## 1. Security — trust first
Without trust, producers won't publish and consumers won't rely on the data. Three concerns beyond "use TLS":
- **Payload encryption (end to end)**: transport encryption (TLS) protects only one hop; events that pass through brokers, routers or other organisations' infrastructure are readable at each intermediary. Where data is sensitive, encrypt the payload itself and keep the envelope readable for routing. Brokers that treat the payload as opaque bytes (MQTT, AMQP's immutable message body, Kafka) can carry encrypted payloads, but there is no common standard for signalling the method or exchanging keys; CloudEvents recommends but does not define payload encryption. Agree it in the contract (e.g., JWE/COSE, envelope keys per consumer, KMS-managed keys — general knowledge).
- **Connection security**: authenticate both ends (mutual TLS with X.509, OAuth 2.0 client credentials or signed tokens), authenticate brokers to clients where devices can't do TLS, protect every step of subscription set-up against spoofing, and sign webhook deliveries (HMAC signature + timestamp to stop replay — general knowledge). Authorise per topic and per consumer; support revocation that takes effect promptly.
- **Data provenance**: a record of the inputs, systems and processes that shaped the data, so consumers know it wasn't altered — even after intermediaries processed it. Options: signatures or keyed hashes over the payload appended per processing step (simple, but the chain itself can be stripped); external tamper-evident logs or ledgers (stronger, slower). No widely adopted cross-party standard yet; this remains an open gap. At minimum: sign at source, keep `source`/`id`, record each transformation's lineage.
- **Privacy** (general knowledge): minimise personal data in events (IDs over profiles), set lawful basis and purpose per stream, remember that retained logs and replays re-expose data, plan for erasure (crypto-shredding, compaction, short retention for personal data).

## 2. Agility — connect and disconnect freely
Flow's value is that consumers and producers can change their connections as they see fit, and the system adapts. Any consumer interested and authorised can attach; when interest or authorisation ends, it detaches predictably with no side effects.
- **Loosely coupled interface**: hides the producer's internals so each side changes on its own schedule. Two ends of a spectrum: subscribe by topic/subject name without knowing where it's served (messaging-style URIs), or plain HTTP resources and verbs. Expect hybrids: HTTP to locate and set up, stream-specific mechanics for flow control, errors and routing. No single standard subscription interface has won yet.
- **Known, predictable protocol**: the failure of many ESB programmes was the lack of one shared data protocol — every integration through the bus cost almost as much as a direct one. Separate **metadata** (what, from where, when, encoded how, encrypted how — ideally in the event so it survives routing) from **payload** (domain data). Standardise the envelope now (CloudEvents); expect payloads to be stream-specific at first (JSON/Avro/Protobuf with a schema), converging on industry standards later.
- **Schema evolution** (general knowledge): register schemas; set a compatibility rule per stream (backward for consumer-safe changes, full where both sides deploy independently); add optional fields, never repurpose or remove without a new version; version the event type (`com.acme.order.placed.v2`) or the schema; run old and new in parallel during migration.

## 3. Timeliness — fit for the use
Data has a half-life: its value for a given action drops after some time (seconds for trading, minutes for logistics, hours for some reporting). Timeliness means arriving and staying available in time to be useful, not necessarily as fast as physically possible.
- **Latency**: network latency (bounded by distance — intercontinental hops cost tens of milliseconds at best — plus hops, queuing and congestion) and processing latency (every inspection, route, copy and enrichment adds up). Mitigations: process near the source or consumer (**edge**), cut hops, process in parallel rather than in series, set a **latency budget** per processing step and measure against it.
- **Retention**: how long an event remains available to consumers. Too short → consumers that were offline lose events and build wrong state; too long → storage cost and harder search. Make retention an explicit producer promise ("available for 7 days"), with a replay or snapshot path for consumers that fall further behind. Data that has landed in a sink follows ordinary data-at-rest retention.

## 4. Manageability — observe and control from your side
Each party can see and act only on what it controls. Two traits:
- **Observability**: find meaningful signals in operational data — a producer that stopped publishing, a consumer seeing duplicates, lag growing. Share *just enough* across the boundary: too little and failures can't be traced; too much costs processing and leaks information. Push streams have no natural error channel (unlike HTTP responses), so: use status codes in the request–response parts (subscribe, renew), heartbeats or expected-rate checks, producer status/operational event streams, consumer lag metrics, end-to-end tracing (W3C Trace Context / OpenTelemetry propagated in event attributes — general knowledge).
- **Controllability**: the ability to change behaviour predictably — reconfigure a subscription, pause, replay, throttle. Generally the producer (or its platform) sets the operating context, as API providers do today; sometimes a dominant consumer does.
- **Emergent failures**: independent agents can create feedback loops no single party intended (circular A → B → C → A; cascading automated trading in a flash crash). Defend with circuit breakers, rate limits, loop detection (hop counts or causation IDs carried in metadata), and resilient agents.

## 5. Memory — replay the past
Some uses need to rebuild state or audit history: financial records, compliance, debugging ("which events did this consumer receive, with what configuration?"), replay into staging to reproduce an incident, simulation and ML on event sequences. Memory costs storage and promises; not every stream needs it. Where it does: log-based retention or archived streams, event sourcing for entities whose history matters, immutable audit topics, snapshots plus tail replay for long histories.

## 6. Control of intellectual property
Owners must stay in control of their data once it leaves them, or valuable streams won't be offered. Needs provenance (so the brand isn't damaged by altered data) and enforceable terms. Once data is on someone else's machine, technical enforcement is weak (cf. digital music before streaming). Levers: streaming access (subscribe rather than copy) which makes repackaging less attractive; time-limited keys or certificates tied to the licence term; per-consumer encryption; watermarking; contracts and usage terms; **monetisation** built into subscription (metered or tiered access with entitlements).

## Quick check (per stream)
Who may subscribe, and how is it enforced and revoked? Is the payload encrypted end to end where needed? Can the consumer verify source and integrity? What is the envelope and schema rule? What latency and retention are promised? How does each side detect silence, lag and duplicates? Can it be replayed, and should it? What are the usage terms?
